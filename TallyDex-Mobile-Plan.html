Section 1

Source audit

Findings from reading all three projects on 14 Oct 2026.

Functionality

TallyDex-FE (web portal)

  • React 18, Vite, MUI 5, TanStack Query, axios. ~21.8k lines across 26 pages.
  • Three roles: SUPEROWNER, OWNER and USER. A SUPEROWNER can also connect to an organization and then sees the OWNER menu (superowner_connected_mode).
  • Pages are gated by 9 module codes from GET /modules/organization/:id, using status === 'ACTIVE': tally_connections, HO_Dealers, HO_Stockitem, Map_Dealer, Map_Stockitem, SecondarySales, SSV_SalesAnalytics, ClosingStock, ClosingStock_Analytics.
  • The menu is built in src/components/Layout.tsx → getMenuItems() and goes up to 3 levels deep (Reports › Sales › All).
  • Tenant endpoints need the x-organization-id header. Each service passes it by hand.
  • On a 401 the app logs the user out. It never calls /auth/refresh-token.
  • On login: if isFirstLogin is set, the user is sent to Change Password. The first organization is selected automatically, and modules and the SSV filter cache are prefetched.
  • The dashboard shows 4 stat cards that depend on the role (GET /dashboard/stats).
  • Reports are wide tables (16 columns in the Sales report) plus Recharts analytics (pie, line and bar).
Theme

TallyDEx_ (design reference)

  • login/: login and change password. White form column, floating-label fields with a warm tint, orange gradient primary button, black secondary button.
  • nav/: portal shell. Black sidebar, grey #EEF0F3 canvas with white cards, white top bar, breadcrumb and an entity (organization) scope switcher.
  • Accent #E46C0C (hover #F07E22, pressed #C95F0A). The active item in the sidebar has a 4px orange left bar.
  • Type: Wix Madefor Display for titles and the brand, Inter for the UI (login uses Wix Madefor Text).
  • Full token set in nav/app.css: surfaces, 4 text greys, status colours (ok, warn, danger, info), radii 14/10/8, shadows, and a dark theme.
  • Components: page head with eyebrow, card head with lead icon, stat tiles, badges, empty states, filter bar, pager, toasts, collapsible cards.
  • The sidebar labels are a proposed future IA (Entity, Rules Activation, Price Level, SyncLog…). Most of these have no API yet, so only the styling is used.
Skeleton

DataLynkr-app (mobile reference)

  • RN 0.81.6 (old arch, Hermes), React 19.1, React Navigation 7 (native-stack + bottom-tabs), TS, axios, zustand, AsyncStorage.
  • Header (StatusBarTopBar): solid brand-colour bar, ≥47dp, 16dp padding. Hamburger or back arrow on the left, then a 17sp/600 title, at most 2 icons on the right. The status bar matches the header.
  • Sidebar (AppSidebar): global, slides in from the left in a Modal. Width = min(89% of screen, 348dp), 280ms animation, swipe to close. Order: logo row, profile card, COMPANY picker, menu list (expandable groups), logout.
  • Footer tabs: white, 1px top border, 24dp icons with 10sp labels. Hidden on detail and form screens.
  • Back button: pops the stack, otherwise shows an Exit dialog. Permissions are deny-by-default.
  • Conventions worth copying: AppText wrapper, colour tokens only, showDialog instead of Alert, a single navigationRef, navigationBarTranslucent on every Modal, 16KB page alignment in Gradle.
  • Fonts already bundled include Wix Madefor Display, so they can be reused.

Structure & navigation

  1. Fixed layers, top to bottom: status bar → AppHeader → optional ScopeBar (tenant screens only) → optional FilterBar / SegmentedTabs → scrolling body → optional sticky action footer → BottomTabBar (tab roots only). Nothing else is pinned.
  2. The header title is the menu label. The title in the header matches the sidebar label exactly. The body has no repeated H1, except the Dashboard greeting.
  3. Left header icon: top-level screens (opened from the sidebar or tabs) show the menu icon. Pushed screens (detail, form, sub-page) show back. Never both.
  4. At most 2 header actions on the right, 22dp icons with 48dp touch targets. Anything more goes in a ⋯ overflow sheet.
  5. One global sidebar. Screens never render their own drawer. The sidebar is built from navigation/menu.ts, which is the only place that decides which items a role or module unlocks.
  6. Max two menu levels (D7). Groups expand like accordions, one open at a time, and the group holding the current screen opens by default.
  7. Android back: closes an open sheet or dialog first, then the sidebar, then pops the stack. On a tab root that isn't Home it goes to Home. On Home it shows the Exit dialog.
  8. Footer tabs hide on pushed screens, forms and detail views (same rule as DataLynkr's ordersTabBarStyle).

Layout & content

  1. Canvas and cards: the screen background is canvas. Content sits in white Cards (radius 14, 1px line border) with a 16dp gutter and 16dp gaps.
  2. No web tables on phones. A table becomes a list of card rows: one primary line (name), one secondary line (at most 3 key fields separated by ·), and a right-aligned value or badge. Tapping a row opens a detail sheet with every column as key/value pairs.
  3. Numbers: tabular figures, right-aligned. Currency is ₹ 1,23,456.00 (en-IN). Dates are DD MMM YYYY, and times DD MMM, HH:mm.
  4. Tabs inside a screen: 2–3 options use a SegmentedTabs control. 4 or more use a horizontally scrolling tab strip (for example, User Management).
  5. Filters: a row of chips under the header shows the active filters (date range first). A "Filters" chip with a count badge opens a bottom sheet with Apply and Reset. An empty selection means "all", as in the API.
  6. Lists paginate with infinite scroll. Page size is 20, using the API's page and limit. Pull-to-refresh is on every list and the dashboard.
  7. Scope bar: every screen that sends x-organization-id shows the active organization. Switching organization resets the screen's data and filters.

States & feedback

  1. No blank screens. Every data screen handles four states: loading (skeleton shaped like the content), empty (icon, title, hint, optional action), error (message and Retry), and no access (lock icon and "Ask your administrator").
  2. Permissions are deny-by-default. Until the organization's modules have loaded, gated menu items are hidden. A gated route opened without access shows the no-access state.
  3. Feedback: success uses a toast (bottom, 3s). Form errors appear inline under the field. Server errors appear in a banner at the top of the form. Destructive actions always confirm with a dialog that has a red action button.
  4. One primary button per screen (orange gradient, 48dp, full width on forms, pinned in a sticky footer when the form scrolls). Secondary actions use the dark or ghost style.

Forms & inputs

  1. Text fields follow the login design: the label sits on the top border (12/600), the field has a warm fieldTint fill, turns white with an orange border and 4dp orange ring when focused, and shows a red asterisk when required. Password fields have a show/hide eye.
  2. Pickers never use the native spinner. Single and multi selects open a bottom sheet with search (when there are more than 8 options) and a sticky Done button.
  3. Keyboard: forms scroll so the focused field and primary button stay visible. The return key moves to the next field, and the last field submits.

Code conventions (from DataLynkr)

  1. Tokens only: no hex literals or raw font names in screens. Use theme.colors.*, theme.type.* and theme.space.*.
  2. Wrappers: use AppText / AppTextInput instead of RN Text / TextInput, showDialog instead of Alert.alert, navigateTo from navigationRef, and log instead of console.
  3. System bars: the status bar matches the header (chrome, light content). Every <Modal> sets navigationBarTranslucent and pads its bottom by insets.bottom.
  4. Accessibility: every pressable has an accessibilityLabel and a testID (screen-element). Text scales with the system font up to 1.3×.

Section 8

API contract (draft 1)

From TallyDex API v3.postman_collection.json and TallyDex-FE/src/types. Every response uses the envelope { success, message, data, timestamp }. Error text is read from error.response.data.message.

Login

POST {baseUrl}/auth/login        (no auth)
{ "email": "…", "password": "…" }

200 → data: {
  accessToken, refreshToken,
  user: { id, email, firstName, role: 'SUPEROWNER'|'OWNER'|'USER',
          phone?, isFirstLogin? },
  organizations?: [{ id, name, dbSchema }]
}

POST /auth/refresh-token  { refreshToken }  → same data shape

Other draft-1 calls

  • POST /auth/forgot-password { email }
  • PUT /auth/change-password { currentPassword, newPassword, confirmPassword }. A 401 here means a wrong password, so it must not trigger refresh or logout.
  • PUT /auth/profile { firstName?, phone? } → data.user
  • GET /auth/activity?page&limit → items[] plus pagination
  • GET /dashboard/stats → role, totalUsers, newUsersLast30Days, totalOrganizations, newOrganizationsLast30Days, totalModules, activeTallyConnections, activeUsersLast24Hours, lastLoginAt
  • GET /modules/organization/:orgId → data.modules[] { code, status }
  • GET /organizations?page&limit (SUPEROWNER connect list)
  • Tenant calls send the header x-organization-id: {selectedOrg.id}. The axios interceptor adds it when a request is marked tenant: true.
